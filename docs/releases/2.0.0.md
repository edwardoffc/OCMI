# OCMI 2.0.0

OCMI 2.0 combines selected file memory and explicit orchestration with a native
core for task/resource lifecycle, scoped code context and checkpoint recovery.
Use the [release list](https://github.com/edwardoffc/OCMI/releases) and
[installation guide](../install-system.md) to obtain and verify a matching
ReadyKit. A repository URL or source ZIP is an orientation entry, not an
installation or authorization to configure a client.

## Native home and selected memory

Public payload and the native executable live in `system/`. `OCMI_Sync/` holds
selected portable coordinator/project/topic files; `local/` holds machine-only
bindings and operational state. A verified local kit, bound client project and
initialized coordinator precede opt-in topic storage or project integration.
Occupied homes and installed projects are preserved until an explicit update.

ReadyKit is the native package authority. Profile ZIPs are coordinator inputs,
not complete native installations. The [historical profile receipt](2.0.0-workflow-r4.json)
and its issued archives remain unchanged. The eight-file coordinator template is
legacy compatibility; new homes use flat `OCMI_Sync/coordinator` inputs and local
binding. Personal topic memory is optional, normally in `OCMI_Sync/personal`.

## Task, resource and context lifecycle

Explicit bindings connect a task's Contract, required originals, worker and
checker. Native operations track task state and declared resource lifecycle;
unknown writer or ownership evidence remains pending for inspection.
`context.inspect` provides current facts, selected code context, whole required
originals and a derived ready START. Main explicitly delivers START. Read the
semantic Contract and inputs before acting; keep one PLAN, rationale, unresolved
questions, Result and Acceptance rather than copying machine state after commands.

The optional caller formatter separates decoded compact context from native
metadata and operation output. Direct human text output remains available.
Neither presentation grants authority or establishes semantic completeness.

## Checkpoints and supported limits

File checkpoints preserve explicitly selected files. Git checkpoints preserve
supported committed history, refs, index and work-in-progress for restoration
into another existing-empty directory. Local operation groups retain original
identity evidence; publication does not replace an arrival, and foreign or
uncertain resources are preserved. Portable checkpoint content carries no local
ownership authority. See the [runtime guide](../runtime.md) for supported inputs
and operational recovery boundaries.

Native delivery targets Windows, Linux and macOS on Intel and Apple Silicon.
Provider and client capabilities remain explicit: there is no universal tool
interception, arbitrary same-user hostile-writer isolation or complete clean-OS
reset. Optional/preview features keep their documented limits. Functional
availability does not establish whole-system effectiveness on real tasks or
measured time/token savings. Existing installations require an explicit preserving
update; no automatic scan, installation or client configuration is implied.
