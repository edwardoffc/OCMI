# OCMI 1.2.2 — формат задач и передачи

**OCMI 1.2.2, редакция правил 2026-10-11**

Совместимое обновление процесса OCMI 1; схема карточки и поля существующих экспортёров сохранены.
[ORCHESTRATION](ORCHESTRATION.md) задаёт готовность/проверки/ревью, [RULES](RULES.md) — память.
Проектные команды, модели и полномочия определяются локально; установленная копия самостоятельна.

## Одна карточка на задачу

Путь: docs/memory/tasks/<id>/HANDOFF.md. Точные заголовки:
- `## Contract` — постановка/baseline/ревизия/scope/checks/назначение; меняет главный.
- `## Result` — результат, evidence и продолжение; меняет назначенный исполнитель.
- `## Acceptance` — ревью, решение и интеграция; меняет главный.

Служебный JSON экспортёра перед Contract защищён; его поля не переименовывать.
Большой контракт хранить в пакете по ссылке. Отдельный Result.md не заводить.
В новой карточке — относящиеся к задаче факты, матрица и разница с предыдущей ревизией;
постоянные правила и прошлую историю не копировать. Ссылки должны вести к доступным
зафиксированным входам; одной фразы «как раньше» недостаточно для нового чата.

## START, пакет и продолжение

Инициализация задаёт роль/слот: до START только готовность, без реализации, проверок и Goal.
Запрос промптов не разрешает создавать чаты, отправлять сообщения или менять модели.
START указывает ID/ревизию, точную копию, текущий HANDOFF, baseline, входы и команды.
Продолжение сверяет проект/роль/task/revision/копию и действующий ready START с записью главного;
противоречивый вход не назначает работу. Running — ожидание того же процесса, не дубликат.
Пакет — неизменяемый оригинал; рабочая карточка — текущая сдача, править можно только тело Result.
Изменение контракта/тестов/checker/baseline — новая явная ревизия с сохранением WIP и evidence.
Старый START не назначает новую работу. При новом чате текущий Result не стирать.

## Сдача и приёмка

Result: статус running/review/blocked и дата, baseline/полный diff с новыми/удалёнными файлами,
выполнение критериев, команды/exit codes/pass-fail-skip, среда/зависимости/логи, protected hashes,
reuse и причины повторов, риски/непроверенное, остаток/процессы, предложения для карты и кандидат в урок с evidence/областью/ограничениями.
Модель/усилие, время и расход — фактические с источником/областью либо unknown.
Полные очищенные логи сохранять по разрешённым доступным путям согласно RULES; короткий итог в чат не заменяет доказательства.

DONE — готовность к ревью. Главный проверяет защищённые части до правки Acceptance;
запись Acceptance завершает эту ревизию проверки, не разрешая исполнителю её редактировать.
Решение accepted/rework/blocked, findings, принятая и интегрированная версии фиксируются отдельно.
Учёт продолжается до интеграции; выпуск требует своих оснований. Форма отчёта не доказывает поведение.
Урок принимается главным после проверки; только затем — локальное правило или LESSONS.
Сохранять источник и статус, не переносить локальный опыт в глобальные правила автоматически.
В общей папке передать ID и путь HANDOFF; в другой копии также полный diff/новые файлы и её путь.
Синхронизация между копиями не подразумевается. Консультант передаёт предложения через владельца.

## Закрытие и cleanup

Приёмка, интеграция и завершение ресурсов — отдельные состояния. После интеграции главный
выполняет короткую проверку завершения из своей процедуры и записывает в Acceptance:
- `cleanup: done` — ресурсы удалены в разрешённых границах либо учтены как keep/archive/transfer
  с причиной, владельцем, условием хранения и проверенным доступом к нужным данным.
- `cleanup: pending` — конкретный остаток, причина, владелец, следующее действие и условие повторной проверки.

Если временные ресурсы не создавались: `cleanup: done — временные ресурсы не создавались`.
Неизвестный остаток нельзя считать done. pending не отменяет принятую реализацию/интеграцию
и не запускает повторный цикл тестирования; риск для самого результата оценивается отдельно.
Задача полностью закрыта после интеграции и done; принятая с pending остаётся видимой
в текущем handoff/PLAN по ссылке на Acceptance. Отдельный журнал уборки не нужен.
Исполнитель в Result сообщает ресурсы/WIP/процессы, главный отвечает за завершение в пределах полномочий.
Уборка, изменившая среду или config, требует затронутой проверки; одно оформление — нет.

## Совместимость

Новые правила — для новых назначений/явных ревизий. Выданный checker обязателен:
упрощение отчёта или доказанный reuse не разрешают обойти старые требования.
Старые пакеты и их обозначения сохраняются; обновление комплекта не переустанавливает проекты.
Отсутствующий cleanup в старой карточке — неизвестный статус, не done; не дописывай защищённый пакет.
Для остающихся ресурсов зафиксируй актуальное решение главного в текущем handoff/Acceptance
со ссылкой на старый результат; контрактные изменения оформляй явной ревизией.
