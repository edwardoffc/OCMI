# Достаточные приёмочные проверки

Входы: согласованное поведение/потребитель, риск, существующие проверки с зависимостями, защищённая исходная версия и разрешённые ресурсы. Сначала сопоставьте каждому критерию существующую проверку и объясните достаточность; добавляйте проверку только для существенного пробела.

Выберите настоящего затронутого потребителя и значимые отрицательные случаи. Где нужно, проверьте реальные ID, единицы, форматы, совместимость, остановку/перезапуск и целостность данных. Mock подтверждает только заменённую границу. Для текста не требуются продуктовые сквозные тесты; oracle не должен повторять детали реализации.

Используйте действующий контроль: известный правильный случай и адресное неверное поведение, которое проверка отвергает, либо другой обоснованный oracle. Отличайте нарушение требования от неисправной fixture/среды. Одно отсутствие файла не доказывает поведенческую регрессию.

Для рискованной нестандартной подготовки/конкурентности/транзакций/восстановления проверьте точную предпосылку на настоящем движке/harness до ready. Отделите поведенческий инвариант от наблюдений за планировщиком/внутренним устройством; иной корректный порядок нельзя отвергать без требования. В существующей матрице укажите команду/результат релевантного контроля и ограничения. Статического совета или зелёного контроля другого случая недостаточно. Актуальный контроль используйте повторно; это не отдельная контрольная задача для каждого assertion и не требование заранее реализовать функцию.

Ограничьте контроль предпосылки названным вопросом; объясните переиспользование кода/evidence вместо второй реализации функции. Новые исполнимые fixtures/адаптеры проверьте с реальными аргументами потребителя, совместимыми данными и релевантным контролем в пределах полномочий; один синтаксис/заглушка означают лишь проект. Тесты разработки исполнителя в AllowedPaths отделяйте от фиксированной независимой приёмки.

По умолчанию специалист предлагает соответствие критерия проверке, fixture/oracle, команды, ожидаемые результаты и ограничения. Запись/запуск тестов требуют назначенной области и роли; консультант только на чтение даёт рекомендации. Оркестровщик проверяет предложения до фиксации тестов; выданный защищённый checker меняется лишь явной редакцией.

Используйте действующие доказательства повторно; не запускайте полный suite ради оформления отчёта. Без предпосылки укажите непокрытый критерий и следующую диагностику, не выдумывая покрытие. Результат теста не является приёмкой.
