# Профили хранилища инструментов для обычных запусков

[English](../../../docs/runtime-tool-storage.md) · [Русский](runtime-tool-storage.md)

Этот preview-маршрут позволяет обычной уже разрешённой команде задачи
использовать machine-local профиль хранилища инструмента. Он применяет
объявленные безопасные path settings к этому запуску и до старта команды
учитывает общие хранилища как внешнее использование. Это не установщик
инструментов, не команда миграции хоста, не изоляция ОС и не общий монитор всех
побочных эффектов.

## Через координатора

Попросите координатора проверить существующий одобренный профиль для выбранной
установки и текущей задачи, объяснить запрошенный эффект хранилища/scratch
инструмента и показать результат обычного запуска задачи. Не пишите JSON
профиля и не создавайте папки самостоятельно. Координатор либо использует
существующий одобренный профиль, либо готовит свежую выбранную раскладку через
native authoring; он никогда молча не придумывает профиль или места хранения.
Пока профиль не одобрен и не active, он сообщает setup pending. Задача без
`toolStorage` сохраняет прежнее поведение команды.

Координатор может добавить точную ссылку `toolStorage` при `task.bind` или
явном `task.revise`; затем `task.ready` и STOP checks управляют обычным
запуском. Она называет абсолютный выбранный home установки, tool ID в нижнем
регистре и SHA-256 профиля. Runtime читает только соответствующий
ограниченный профиль из local bindings этого home; он не ищет инструменты по
всей машине и не сканирует кэши или исходники.

Для `task.bind` или `task.revise` необязательное поле команды имеет ровно вид
`"toolStorage":{"home":"ABSOLUTE_APPROVED_INSTALLATION_HOME","toolId":"go","sha256":"APPROVED_PROFILE_SHA256"}`.
Поле `profileSha256` активной квитанции соответствует полю `sha256` ссылки;
не добавляйте в ссылку `profileSha256` или лишние ключи. Используйте явно
переданную одобренную ссылку. Актор проекта не может получить её через просмотр
состояния координатора установки; при отсутствии ссылки нужно уточнение
координатора, а не обход полномочий или исправление профиля. Пример команды
по умолчанию работает без профиля. `ocmi help task.bind` и
`ocmi help task.revise` показывают этот объект как `optionalCommandFields.toolStorage`.

## Preview native authoring

Если соответствующий native runtime предоставляет эту функцию, координатор
подтверждённой установки может выбрать поддерживаемый инструмент и корень
ToolData, показать один конкретный plan и его effects, записать существующую
ссылку на consent владельца, применить неизменённый plan и просмотреть
типизированный результат. Выбранный корень может уже существовать и
использоваться совместно, либо новым может быть только его конечный leaf под
существующим обычным parent; произвольное новое дерево недопустимо.
Пользователь не передаёт JSON. Сам prepare не создаёт внешнюю папку инструмента
или пригодный профиль; apply — это шаг с consent gate, который создаёт одну
свежую папку инструмента и публикует её только после успешной требуемой проверки.

Существующий корень ToolData может обслуживать несколько инструментов, но
неизвестная существующая папка отдельного инструмента никогда не принимается и
не перезаписывается. Результат `inspect` различает
`effective-paths-verified` для фиксированных процедур Go/npm и
`path-variables-only` для пользовательского инструмента; переменные его
пространства имён не доказывают, что provider принимает или использует их.
Типизированный отказ, незавершённая транзакция или результат `recover`
сохраняют свидетельства, а не придумывают профиль, не повторяют проверку и не
удаляют созданные данные.

Для фиксированной проверки Go `HOME`, `APPDATA` и `XDG_CONFIG_HOME` сначала
направляются в owned probe scratch. Первая supervised-команда Go выключает
telemetry без изменения пользовательских настроек; затем свежий фиксированный
запрос `go env` проверяет этот режим, каталог конфигурации telemetry и
объявленные пути. Типизированный отказ или неопределённая уборка остаются
свидетельством pending, а не purge. Это не предотвращает каждого detached child,
не предоставляет универсальную песочницу и не переносит данные хоста. См.
[Go telemetry](https://go.dev/doc/telemetry).

### Машинная справка для координатора

Используйте существующий запрос `ocmi request` с `rootKind: "installation"`,
`actor: "coordinator"` и `expectedRevision: 0`. Поддерживаемые действия:
`tool-storage.prepare`, `tool-storage.apply`, `tool-storage.inspect`,
`tool-storage.cancel` и `tool-storage.recover`; неизвестные или лишние keys
отклоняются. Пользователь по-прежнему обращается обычным языком, а координатор
формирует запрос из выбранной установки и одобренных входов.

`tool-storage.prepare` содержит ровно `toolId`, `toolDataRoot`, `owner`,
`purpose`, `retention`, `maxBytes`, `maxAgeDays`, `executable`, `script`,
`stores` и `scratchEnv`. Укажите абсолютный выбранный корень ToolData, владельца,
назначение и условие хранения; размер задаётся в байтах, возраст — в днях.

| Инструмент | `executable` | `script` | `stores` / `scratchEnv` |
| --- | --- | --- | --- |
| `go` | Абсолютный путь к Go | `""` | `[]` / `[]`; фиксированные настройки Go |
| `npm` | Абсолютный путь к Node | Абсолютный путь к `npm-cli.js` | `[]` / `[]`; фиксированный кэш npm |
| Произвольный slug | `""` | `""` | Явные пути и временные переменные своего пространства имён |

Например, `widget` может объявить `stores: [{"key":"WIDGET_CACHE","path":"cache","kind":"cache"}]`
и `scratchEnv: ["WIDGET_TMP"]`. У хранилища ровно три поля: `key`, `path`, `kind`
(`cache` или `data`); путь отсчитывается от нового подкаталога инструмента.
Для `apply` и `recover` требуются ровно
`toolId`, `planId`, `planSha256`, `consentReference`; для `inspect` — `toolId`;
для `cancel` — `toolId`, `planId`, `planSha256`. Эти имена API предназначены
координатору, а не предлагают пользователю вручную писать JSON.

## Что делает opt-in запуск

До появления эффектов команды runtime повторно проверяет выбранные профиль,
home, корень ToolData и каждое объявленное существующее хранилище по native
identity и raw hash профиля. Затем он учитывает каждое общее хранилище как
существующий локальный ресурс с mode `use`, внешним ownership, объявленными
owner/purpose/retention и disposition `release`. Обычная операция сохраняет
использование, пока наблюдаемая команда не завершится; подтверждённое закрытие
освобождает запись использования.

Path-only variables применяются к дочернему процессу, а не сохраняются как
настройка машины. Разрешённые profile keys: Go `GOCACHE`,
`GOMODCACHE`, `GOPATH`, `GOBIN` и npm `npm_config_cache`. Другой инструмент
может использовать только объявленное пространство имён его uppercase slug для
path-only settings. Фиксированные процедуры Go/npm native authoring проверяют
effective paths в свежем наблюдаемом процессе; пользовательские инструменты
остаются `path-variables-only`. Runtime TMP остаётся scratch самой операции: объявленный
Go `GOTMPDIR` или scratch alias пространства имён инструмента указывает на
точный scratch, а не на общее хранилище.

Сам профиль объявляет существующий корень ToolData, максимальные bytes и age,
stores (cache или data), безопасные store environment keys и scratch keys. Это
закрытые метаданные для проверки; запуск не создаёт ToolData или stores, не
меняет профиль, не выполняет age/space purge и не выдаёт право удаления.

## Общее использование — не ownership

Один machine-local профиль могут использовать задачи двух проектов. Каждая
задача получает своё свидетельство use/release; ни одна не получает ownership
над общим cache или data. Проект не может удалить общее хранилище только потому,
что использовал его. Неизвестное, pending, failed или непроверенное closure
остаётся видимым для review, а не называется завершённым.

Существующие stores только используются, кроме описанного ниже ограниченного
сохраняющего переноса. В этом preview нет команды установки, произвольного
переносчика хоста, автоматического cache-pruning или миграции global-конфигурации.
Сохраняйте старые данные, если профиль отсутствует,
неверен, заменён, не поддерживается или не проходит повторную проверку.

## Preview сохраняющего переноса

Для текущего native-approved профиля Go или npm с lifecycle schema2
подтверждённый координатор может подготовить один выбранный свежий ToolData.
На этапе prepare он лишь показывает этот выбор; для apply требуется явно
одобренный владельцем неизменённый plan. Копируется только полный ограниченный
набор известных stores, а исходная и новая копии сохраняются. Переход не
начинается, пока есть активное использование либо использование, которое не
удалось надёжно завершить или проверить. Перед публикацией нового generation
apply доказывает свежие пути provider; inspect показывает выбранные старое и
новое расположения, известное использование и следующее действие.

Маршрут координатора: `tool-storage.relocate.prepare` →
`tool-storage.relocate.apply`; `tool-storage.relocate.inspect`,
`tool-storage.relocate.recover` и `tool-storage.relocate.rollback` относятся
только к этому переходу. В первой поддерживаемой версии допускается не более
1024 файловых записей общей величиной до 16 MiB.

Rollback использует тот же одобренный переход и отказывает, если новые данные
изменились. Прерванное состояние остаётся доступным для inspect и имеет статус
pending; recover закрывает только доказанную фазу метаданных и не повторяет
недоказанный дочерний процесс. Поведение schema1 для исторических и вручную
созданных профилей, а также отсутствие профиля, не меняются и не обновляются
молча. Средство обновления не должно выбирать для применения или отката поколение
системы, если при действующих профилях schema2 в build-info этого поколения
отсутствует поле верхнего уровня `toolStorageProfileFormat` со значением `2`.
Старый читатель с закрытой схемой отклоняет метаданные schema2.

## Свежесть и отказ

Runtime отказывает supplied malformed profile, а не игнорирует его. Он также
отказывает при изменённых bytes, same-byte replacement профиля, изменённых или
отсутствующих home, ToolData или store identity, links/reparse points,
небезопасных путях, reserved или case-colliding environment keys и профиле,
пересекающемся с выбранными project или home. Проверка повторяется
непосредственно перед launch: замеченная гонка может оставить inspectable
свидетельство операции, но не позволит старт с непроверенными путями.

Переменные профиля не могут менять `PATH`, home/profile locations, обычные OS
data roots, dynamic-loader variables, общие environment loaders, Node/Python
options, постоянную/default Go-конфигурацию или `TMP`/`TEMP`/`TMPDIR`. Это
намеренно: path setting не даёт полномочие заменять окружение хоста или
настраивать произвольного provider.

## Текущая граница

Маршрут применяет уже одобренный профиль к обычной команде задачи. Описанный
выше preview native authoring добавляет создание свежих layout/profile,
фиксированную проверку путей Go/npm и только описанный сохраняющий перенос
lifecycle schema2. Он не добавляет host installation или global settings,
source deletion существующих данных, автоматическую очистку по capacity/age,
универсальное наблюдение
background/remote effects, Docker/Codex automation, установку инструментов хоста
или команду миграции глобальной конфигурации. Compatible update установки сохраняет закрытые active
profile и receipt; malformed или pending authoring state отклоняется до effects
обновления. Остальные возможности нельзя выводить из успешного обычного запуска.

Координатор может запросить `tool-storage.maintain.inspect` для одного
выбранного текущего кэша Go/npm с lifecycle schema2. Это ограниченное измерение
только для чтения: оно сообщает policy thresholds, наблюдаемые size/age и known
use, но не удаляет и не изменяет shared external data (`mutationSupported` имеет
значение false).
Измерение ограничено 1024 entries и 16 MiB; thresholds никогда не дают право
на удаление. Очистка остаётся существующим [resource workflow для созданного
воспроизводимого кэша](runtime-resources.md), а не полномочием над shared stores.
Ненаблюдаемый внешний provider остаётся pending.

Для диагностики выбранного проекта до задачи см.
[восстановление окружения](runtime-environment.md). Его маршрут inspection
остаётся отдельным от этого opt-in preview потребления команды.
