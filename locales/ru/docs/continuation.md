# Производное продолжение и ограниченный контекст

## Компактная native-задача

1. Привяжите выбранную задачу и отметьте её ready через существующий API, указав обязательные оригиналы и привязанный checker.
2. Запросите `context.inspect` с `{"mode":"start","taskId":"TASK","taskRevision":1,"worker":"WORKER"}` и CLI `--format text`; укажите выбранный корень/actor и при необходимости ожидаемую ревизию.
3. Тело текстового START равно точному native `data.start`: main явно передаёт его один раз без переписывания и отдельного START-файла. Передаче через инструмент/канал нужны свои полномочия; представление — наблюдение, не назначение.
4. До записи исполнитель использует compact с переданным `data.bindingRef` как `expectedBinding` и читает текущие смысловые оригиналы по маршруту ниже. После чтения смысловых критериев проверки запускается только привязанный checker.
5. Compact-пример: Result: «Добавлены оба примера и ожидаемый JSON; evidence: core operation ID». Acceptance главного: «Соответствуют CLI; прежний текст сохранён». При наличии — отклонение, непроверенное или реальное исключение. В чат — результат и ссылка; core-факты не копируются.

Для малорисковой правки README достаточно такого смыслового Contract:

```text
Результат: читателю README — верные count/no-match примеры; остальной текст сохранён.
Проверка: семантика CLI и привязанный docs check.
Scope: README.md/Result; код/тесты/приёмка защищены.
WIP: сохранить текущие правки.
Решение: docs only; смена поведения — ревизия владельца.
Ресурсы: main хранит файлы/evidence до ревью.
```

ID, машинные факты и общие правила не входят в пример; ссылайтесь на проверенные факты core. Неизвестный/чувствительный риск и файловый режим сохраняют полные guards.

Для ревью — один свежий compact с нужными полными оригиналами/текущим Result/state/revision, без предварительного повторного status/чтения текстов. Output/ресурсы читайте по реальному вопросу.

### Полный контекст и сохранённая квитанция

Для обычного чтения человеком/чатом используйте, например,
`ocmi call --root ABS --actor ACTOR --action context.inspect --format text --payload '{"mode":"compact","files":["rules.md"],"requiredFiles":["input.txt"],"budgetBytes":4096}'`.
`ocmi request --format text` также принимает request envelope через stdin. `files` — повторно используемый
контекст роли; `requiredFiles` и активный Contract передаются целиком в разрешённой текстовой области.
`terms` не используется. START отдельно перечисляет точные привязанные корневые
`.gitignore`/`.gitattributes` в `data.metadataOnlyFiles`: это защищённые binding
метаданные, а не обязательный текст. Явный запрос их текста через compact
отклоняется с `CONTEXT_METADATA_ONLY`. Исключайте их из текстового чтения только
если смысловой Contract не требует содержимого; иначе нужен согласованный
читаемый оригинал. Активный metadata-only Contract также безопасно отклоняется:
нужен одобренный читаемый Contract/ревизия задачи. Остальные ограничения области
и приватности сохраняются; отказ не выдаёт контекст или утверждение о свежести.

Передавайте непрозрачную base64url-квитанцию `receipt` только для удерживаемого
в этом чате контекста; новый/неуверенный чат её опускает. Core заново проверяет
оригиналы: неизменённый контекст указывается в `retainedFiles` без повтора;
`receiptUnchanged:true` сохраняет квитанцию. Изменённые байты или native-замена
с теми же байтами возвращают полный оригинал и новую квитанцию. Она не хранит
исходники и не даёт полномочий. Первичная настройка и повторное использование видимы отдельно.

Compact `expectedBinding` использует `data.bindingRef` переданного START:
нужны ready-привязка, STOP false и отсутствие неразрешённой активности. До действий
читайте Contract/обязательные оригиналы целиком. Native run/submit/review/integrate
проверяют bindings; не дублируйте их ручными SHA-скриптами по файлам. Защищённые
тесты, STOP и владение ресурсами сохраняются. Integrated/cleanup-done задача
может опустить незапрошенный исторический Contract; привязанные оригиналы проверяются.

Compact-текст сохраняет типизированный заголовок, state/STOP/freshness,
retainedFiles, новую receipt и полные оригиналы. JSON по умолчанию остаётся
для программного разбора или работы с квитанцией при необходимости; text —
только CLI compact/start, не mutations/summary/selected/MCP. Отказ — полный
JSON с ненулевым exit; небезопасный raw text заменяется полным JSON.
Бюджет контекста включает подписи (4096 по умолчанию, диапазон 128..65536);
нужный текст не обрезается, типизированный отказ указывает требуемые байты.
Измеренная экономия не заявляется.

Это preview-руководство описывает native-маршрут `context.inspect` в соответствующем runtime. Он помогает человеку или координатору начать с текущих операционных фактов, а затем намеренно читать только файлы задачи, отвечающие на реальный пробел. Он не заменяет человеческие PLAN, обоснование, неразрешённые вопросы, handoff или разрешения самого проекта.

## Обычный порядок

1. Явно сохраняйте выбранный корень. Для вопроса только о состоянии используйте summary; для ревью — консолидированный compact выше.
2. По summary посмотрите текущее назначение, STOP/состояние операции и следующее действие. Это наблюдение, а не разрешение продолжать работу.
3. Выбирайте небольшой набор именованных файлов и буквальных идентификаторов лишь когда назначение оставляет конкретный вопрос без ответа. Расширяйте выбор, если ответ сообщает о пропусках или неполноте.
4. Пусть люди или агенты фиксируют только изменившиеся смысловые решения, PLAN и остаток работы. Не копируйте вручную task/STOP/operation/cleanup-состояние или счётчики между документами: core выводит эти операционные факты. После значимых правок или изменения состояния следующий запрос должен получить свежий вид.

Для установки координатор сперва подтверждает связь с клиентом и использует выбранный home. Для рабочего проекта оркестровщик выбирает корень и фиксирует назначение; исполнитель получает это ограниченное назначение, а не ищет проект или связь с клиентом. Сводка — одноразовое свидетельство сессии; приведённый выше derived START требует явной передачи и сам по себе не является приёмкой или разрешением менять файлы.

## Необязательное наблюдение summary

Native request CLI получает один JSON-запрос через стандартный ввод. Замените `ABSOLUTE_SELECTED_ROOT` корнем, уже выбранным для задачи; не подставляйте Git-метку, URL или другую рабочую копию.

```json
{
  "schemaVersion": 1,
  "action": "context.inspect",
  "projectRoot": "ABSOLUTE_SELECTED_ROOT",
  "rootKind": "project",
  "actor": "main",
  "requestId": "continuation-summary-001",
  "expectedRevision": 0,
  "payload": {"mode": "summary"}
}
```

Этот JSON — технический пример для агента/инструмента; обычному пользователю не нужно его заполнять. Его actor — уже назначенный/привязанный actor (`main` здесь), а не роль, выведенная из запроса. Передайте объект в `ocmi request`. Успешный summary сообщает текущее native-состояние, привязанное назначение/происхождение, ограниченное текстовое резюме и `inputFreshness: "not-read"`. Он не читает исходники задачи и не утверждает, что задача готова, завершена или полностью понятна. `expectedRevision: 0` наблюдает текущую ревизию; положительное значение требует точного совпадения ревизии.

## Выбирайте только пробел

Когда summary и человеческий handoff называют точный вопрос, запросите именованные файлы и буквальные идентификаторы. Например, ниже запрашиваются привязанные входы плюс два явных файла и термины, находящие обработчик запроса и его тест:

```json
{
  "schemaVersion": 1,
  "action": "context.inspect",
  "projectRoot": "ABSOLUTE_SELECTED_ROOT",
  "rootKind": "project",
  "actor": "worker-1",
  "requestId": "continuation-selected-002",
  "expectedRevision": 0,
  "payload": {
    "mode": "selected",
    "files": ["runtime/internal/service.go", "runtime/internal/service_test.go"],
    "requiredFiles": [],
    "terms": ["Handle", "status"],
    "budgetBytes": 16000
  }
}
```

Этот actor также уже назначен/привязан (`worker-1` здесь). Привязанный contract и `requiredFiles` всегда читаются целиком; contract никогда не сокращается до выдержек. Привязанный вход, не названный явно в `files`, также по умолчанию остаётся целым. Привязанный исходник, явно названный в `files`, может вернуть только релевантные выдержки, если он не указан и в `requiredFiles`, но его полные байты всё равно читаются и проверяются hash против привязки. Каждый оригинал, который START требует прочитать модели целиком, помещайте в `requiredFiles`. Для остальных выбранных файлов terms обязательны. `budgetBytes` ограничивает UTF-8 текст выдержек; ограниченные метаданные учитываются отдельно. Пути простые, относительные и ограничены корнем: нет автоматического сканирования репозитория, открытия каталогов, shell-команд, сети, постоянного индекса или автоматической записи памяти. Этот маршрут не читает скрытые/генерируемые/приватные места, ссылки, базы, архивы, ключи или исключённые каталоги. В installation home кодовая выборка ограничена публичным текстом корня, `system/**` и `OCMI_Sync/coordinator/**`; личные темы, recovery-данные и `local/**` в неё не входят.

Ответ явно перечисляет excerpts, обязательные входы целиком, пропуски, уведомления, кандидаты outline, происхождение и метрики чтения. `inputFreshness` показывает, были ли проверены защищённые байты привязанных входов; он не утверждает, что модель получила каждый их байт. В текущем процессе кэшируются лишь ограниченные факты разбора; исходники не сохраняются, а новый CLI-процесс начинается без кэша. Возвращённый исходный текст всё равно может быть конфиденциальным.

## Считайте неполноту и устаревание свидетельством

`CONTEXT_SELECTED` — полезное чтение ограниченной области, не семантический анализ зависимостей. Он по-прежнему сообщает `readiness: "not-evaluated"`, `coverage: "explicit-files-only"` и `completeness: "not-established"`.

`CONTEXT_INCOMPLETE` возвращает безопасные частичные данные с видимыми пропусками или уведомлениями: следуйте указанному nextAction, сузьте/расширьте явную область или вручную проверьте отсутствующий вход. `CONTEXT_INPUTS_CHANGED` намеренно не возвращает excerpts, если изменились привязанные входы задачи: проверьте и пересмотрите ту же задачу. `CONTEXT_CHANGED` означает дрейф корня, состояния или исходника во время чтения; создайте новый запрос, не объединяя его со старым результатом. Неверная или небезопасная область отклоняется без excerpts. STOP остаётся значимым для новой работы, но наблюдение только для чтения может объяснить остановленное состояние.

## Внедрение и пределы

Существующие установленные templates, ZIP, receipts и документация проекта остаются выданными как есть. Позднее внедрение ведёт координатор: свяжите существующие человеческие PLAN и handoff с этим руководством, сохраните их историю и локальные правила и не копируйте операционный статус в несколько документов. Не переписывайте действующий проект и не считайте производный вид инструкцией миграции.

Маршрут остаётся preview-функцией до квалификации релиза. Он не обещает связь с клиентом, широкую авторизацию инструментов, доверие клиента, семантические межъязыковые ссылки, полную карту кода, автоматическое обнаружение незарегистрированных инструментов или ресурсов либо измеренную экономию времени/токенов. Существующий core сохраняет собственный операционный учёт. Подробнее о request envelope и границах операционного восстановления — в [runtime](runtime.md), об необязательном переносимом PowerShell helper — в [context](context.md).
